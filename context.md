### Start the demo

Run `node tools/workspace-server.mjs` with Node 24 from the project folder, then open the [local dashboard](http://127.0.0.1:8790). For a C72 connected over ADB, forward handheld localhost to the PC with `adb -s <device> reverse tcp:8790 tcp:8790`. The Dev APK uses package `be.keypharm.rfid.poc.dev`. The [connected demo guide](docs/connected-poc.md) covers signing, build prerequisites, and a complete rehearsal. Use the shared demo sign-in once per interface, then switch roles using the Role selector.

| Role | Demo responsibilities |
| --- | --- |
| Administrator (Test lead) | Imports receipts and manifests, prepares outbound sessions, manages reader power, and can approve and dispatch from the dashboard. |
| Operator | Scans receipt Product Identifiers and carton EPCs, runs stock counts, and verifies outbound pallets and cartons on the C72. |
| Supervisor | Records the outbound physical check, reviews count results, and dispatches sessions with approval. |
| Reviewer | Records dispatch approval on the dashboard. |

### What to present

1. **Inbound.** The Administrator imports a receipt CSV in **Inbound**. The optional `product_identifier` column accepts a barcode, SKU, or supplier reference. The Operator opens the task on the C72 and selects **Scan barcode**. **Demo barcode** starts enabled. Clear it for the integrated barcode reader with camera fallback. The RFID reader stops after the first valid EPC. **×** discards an unconfirmed read. **Confirm** links the EPC to the product and saves it to the receipt and inventory. The dashboard shows the saved result after refresh.
2. **Inventory and count.** The demo starts with 20 Physalis, 15 Tiger Balm, and 35 Biotona cartons. Generated labels use the product, a demo size (`XS`, `S`, `M`, or `L`), and a number, for example `Physalis-M-01`. Inventory shows **On hand** and **Dispatched**, with per-carton EPC and movement history. The Administrator’s Destination menu includes Receiving, Storage, Staging, and Hold. It disables the current location. A hold requires a reason and confirmation. Open a count in the dashboard, scan the location on the C72, and review the result as Supervisor. Use count simulation for synthetic demo tags.
3. **Outbound.** After the Supervisor records the physical check, the Operator identifies the pallet first and scans its cartons. Missing or extra EPCs block **Continue**. A repeat after a discrepancy supplies a reason from the earlier scan. A repeat after a clean scan requires a reason from the Operator. After accepting a clean match, the final review starts with editable text **Successful Run**. The signed-off review saves the final wording. The dashboard supports individual and batch dispatch. Dispatch updates stock in the same database transaction. Before dispatch, the Administrator can reopen a closed session or replace its CSV while preserving earlier scan evidence.
4. **Reset.** **Reset demo data** restores the 70 starting cartons. The connected handheld drops queued records from the old dataset when it detects the reset.

### Dashboard manifest generation and reader settings

- In **Generate manifest**, the Administrator selects a connected handheld and requests a pallet scan. The Operator opens the assigned task. The handheld scans for about 850 ms, stops automatically, and previews the EPC with the strongest reported RSSI. Tap **×** to discard it and scan again. **Send Scan** asks for confirmation before submitting the EPC to the dashboard.
- The Administrator selects on-hand cartons and previews product names, EPCs, and pickup locations before generating the manifest. **Download CSV** uses the selected dashboard role and saves `pallet-manifest.csv`. The manifest can also create an outbound session directly. **LookUp** on the handheld can search by a manifest's pallet or carton EPC and shows signal strength with RSSI and proximity beeps.
- **Session controls → Administrator settings** configures outbound, stock task, pallet capture, and LookUp power from 5 to 30 dBm. Outbound defaults to 30 dBm and supports per-session overrides. Stock tasks default to 10 dBm, and pallet capture for manifest requests defaults to 15 dBm. A blank LookUp setting uses the selected session's power.
- Administrators can remove an outbound session or a pallet manifest after confirming. Removed sessions disappear from the dashboard and the handheld after sync. Scan history and inventory are preserved. Removing a manifest leaves any session created from it available. The handheld bottom bar uses icons for **Home**, **LookUp**, and **Settings**.

- The carton picker shows on-hand cartons with no pallet assignment in a saved manifest or outbound session. The server checks the assignment again when saving. Inventory still counts assigned cartons as on hand until dispatch.
- Open **Add another pallet** from a ready manifest. **Add existing pallet** moves a saved pallet and its carton assignments from another ready manifest. Pallets already in an outbound session are unavailable. The source keeps any remaining pallets and leaves the active list if emptied. **Request new pallet scan** sends a new tag request to the assigned handheld, then the Administrator maps the cartons.
- Download one CSV or create one outbound session for all pallets. After the physical check, scan each displayed pallet tag and its cartons in CSV order. **Next pallet** requires a clean match for the current pallet. Dispatch requires clean matches for all pallets and deducts all their cartons together.

## Requirements and decisions

The source is Marc Flederus's *Keypharm Mobile RFID Application — Functional Design for Proof of Concept and Pilot*, v1.0, 17 November 2026. The source document stays outside this repository. [POC and Pilot scope](docs/poc-and-pilot-scope.md) maps its requirements and acceptance scenarios. [Approved design](docs/demo-design.md) and [questionnaire](docs/questionaire.md) record the user decisions and their status.

- The POC runs locally on one C72. It covers outer cartons and tagged pallets, physical contents verification, reader configuration evidence, independent scan attempts, local records and evidence export. The source sets a one-day test and up to 500 RFID labels.
- A pallet is identified on a dedicated scan screen. Pallet and carton scans both use the current power selected by the Test lead. Other tags can be present during pallet identification. A manifest CSV may hold several pallets. Any tag of a loaded pallet (pallet tag or carton) can lock it; with several pallets the one whose tag reads with the strongest RSSI wins, then the one with more tags read. The lock, its RSSI and the EPCs observed are kept with the attempt and logged. After the lock only that pallet's cartons count; tags of another pallet in the file are flagged as belonging to that pallet, unknown tags as outside this pallet, and both keep the run on Hold (decision 2026-11-23). The pallet EPC stays separate from carton counts. The carton step still flags unexpected tags.
- Hold the physical trigger to start inventory. Release to stop and finalize. Repeat key events during the hold count as one attempt. Keep Continue disabled during capture and for interrupted runs, missing EPCs or any unexpected EPC. A run with all expected tags plus an extra is 100% complete and stays on Hold. Investigating an extra tag records a log and requires a clean rescan.
- Pallet and carton scanning have dedicated screens. On the C72 a scan runs from the on-screen Start scan / Stop scan button or by holding the trigger. Unexpected EPCs can be marked investigated, removed from zone, neighbouring tag or unresolved. An attempt counts distinct carton EPCs and stores repeat count, first/last timestamps and RSSI if available. Each rescan starts empty and requires a reason. Previous and current results show the EPC evidence and which cartons are newly seen or still missing. First-pass metrics stay visible.
- The Sessions screen holds one PoC test plan for the day; records link to planned tests by Test ID, and the plan shows Done, In progress, Not run and unplanned tests. Closing the PoC day needs every started test closed, a reason for each test not run, and a sign-off. Run notes are logged per run and appear in the export Notes column. Keep failed attempts as evidence. Session closure records reviewed coverage, skipped-test reasons and sign-off. Continue confirms a clean pallet result. Any unexpected EPC keeps the run on Hold, even after it is marked investigated, removed from zone or neighbouring tag; the marking is evidence only. Continue unlocks only after a rescan reads every expected carton and no unexpected EPC (decision 2026-11-23, checklist gap 6). Closure can document a failed test.
- The Test lead loads and revises the manifest and can adjust the idle reader's output from 5 to 30 dBm; ETSI stays read-only. Reader power is the first row of the home screen (**C72 reader**, showing region and power; tap it to change) and in a hardware session under **Details → Reader settings**. Other roles see the current setting and a **Switch to Test lead** button. A change made in a session is logged there; a change from the home screen has no session to log to, and every scan still records the power it used. Supervisor verifies contents and can sign off. Operator and Test lead run scans and confirm clean matches. Reviewer has read access. Roles are local and unauthenticated; the entered person name signs records and fills the Operator and Reviewer export columns.
- Navigation (0.7, decision 2026-11-23): the name and role menu sits in the header, top right; the "Handheld POC" label is gone. The session list shows each test's next step. A session screen shows a Cartons / Verify / Scan / Close strip and one card for the step due now; when another role owns that step, the card offers **Switch to …**. Setup, the carton list and revisions, verification, reader settings, the log and per-test export fold under **Details**.
- Home layout (0.7.4): reader row first, then the sessions as one list (each row shows its next step; Hold, Incomplete and Interrupted in red), then the test plan and evidence. Section titles sit outside their cards, foldouts are list rows with a chevron, and **New test session** sits in a bar pinned to the bottom of the screen (thumb reach). Based on the Android settings pattern (show current values at a glance) and rugged-handheld guidance (48 dp targets, primary action within thumb reach).
- Manifest generator (0.8.0): in the Cartons step the Test lead taps **Build from scan**, scans one pallet's tags (Start/Stop or the trigger; scanning again adds to the list), unticks strays, picks the pallet tag (the strongest signal is preselected) and sets the pallet reference (default `PAL-<Test ID>`) and an optional SKU. Cartons are numbered `Carton 01…` in EPC order. **Use as manifest** loads it like an imported CSV (reserve/candidate labels, then Save manifest). **Save CSV file** opens Android's file picker with `manifest-<Test ID>.csv` as the suggested filename. The CSV rules live in `manifestCsv` in model.mjs (pallet reference and SKU may not contain `, ; "` or start with `= + @ -`, so the saved CSV cannot carry an Excel formula); the builder has its own capture id, so it never touches session scan runs.
- Functional design gaps closed in 0.8.3: (1) FR-04: cartons without a SKU are named before scanning, on the import preview, the Verify step and the carton list, and the count goes into the Manifest saved log (`missingSku` in model.mjs). A blank SKU stays allowed; one carton reference listed twice is still rejected. (2) Section 9.1: every run stores reader profile version `C72-ETSI-1` (`PROFILE_VERSION` in C72Reader.java; bump it when the approved profile rules change), exported in a new last column `ProfileVersion`. (3) Section 13 recovery: Sessions → Evidence shows which sessions changed since their last export (`unexported` in model.mjs, `exportedAt` per session, set when the share sheet opens; Android does not report a cancelled share). (4) Section 10 manifest import error: a rejected file is logged in the session as **Manifest import failed** with the file name and first errors (skipped while no name is set). 
- Functional design gaps closed in 0.8.4 (shipped as 0.8.6): (1) FR-33: a search box on the home screen (shown from two sessions) filters by test ID, pallet, carton, SKU, location, level, people, date (`2026-11-24`) and next step; every word must match (`matchesQuery`). (2) AT-02: each run's result has **By SKU** (expected, matched, missing per SKU; `skuBreakdown`). (3) FR-19: the rescan reason offers the design's five reasons and still takes free text. (4) Section 9.3: Hold is shown as **Hold: unexpected reads** (`statusLabel`); the stored status stays `Hold`. (5) Section 6 home: a line shows PoC Test mode, the device model and whether a network is present (not required). (6) FR-35: a reader power change from the home screen goes to a device log (`store.audit`, shown under Evidence → Device log, exported as `Device log` rows and in the summary); a change inside a session stays in that session's log. (7) Section 12: the summary export adds **Results by configuration** (product / label / position / level / method / shielding): per session first-pass and final completeness and run count, and the first-pass range across sessions as repeatability; segments are never averaged together. A global `[hidden] {display:none !important}` rule makes hidden buttons actually hide. Not built, by design: Pilot mode (FR-01) and the other Pilot items, photos (FR-27; the PRD keeps notes only, and photos would need file storage outside localStorage), and an administration screen (the PRD keeps a name list, reader power and the test plan).
- Saved state (0.8.0): records stay in localStorage `keypharm-poc-v1`. Separately, `keypharm-poc-ui-v1` keeps the open screen (reopens the same session after a restart; a scan or build in progress lands on its session) and half-typed form fields per session, cleared once the form is submitted. Reader power and file inputs are not kept as drafts.
- The Test lead can select **Sessions → Evidence → Reset all local data**. Confirming clears this app's local sessions, manifests, scan attempts, audit logs, test plan and sign-offs, saved names, last screen, and form drafts. Reset publishes an empty dashboard snapshot, stops sharing, and returns to Sessions as Operator. Cancel keeps the current records and drafts. Use **Export CSV and summary** before resetting if you need the evidence.
- The dashboard is a read-only view of records and logs. It fetches when it can reach the running handheld app. An open browser can display its last fetched copy if the handheld goes offline. Handheld scanning, saving and evidence export work offline.
- Pilot is future work. It adds a defined outbound transaction, agreed manifest/result exchange, operational roles, Accept/Hold policy and audited supervisor exceptions. Wrapper automation, label writing or printing, and retail-item tagging are outside this POC.

## Current implementation

The Android app packages local HTML, CSS and JavaScript in a WebView. Java connects to the Chainway SDK, handles physical keys and scan lifecycle, opens the Android file picker and share sheet, and serves the dashboard on the demo Wi-Fi. The core comparison and CSV rules are plain JavaScript and can run in Node for testing.

| Area | File |
| --- | --- |
| Provisional CSV schema, validation, role permissions, trial label accounting, comparison and export | [model.mjs](app/src/main/assets/model.mjs) |
| Local sessions, identity menu, next-step card, reader card, scans, recovery, verification, sign-off, reset and dashboard sharing controls | [handheld.mjs](app/src/main/assets/handheld.mjs) |
| Android bridge, physical trigger mapping and file handling | [MainActivity.java](app/src/main/java/be/keypharm/rfid/MainActivity.java) |
| Chainway initialization, ETSI and power readback at connect and at the start of every run, and inventory | [C72Reader.java](app/src/main/java/be/keypharm/rfid/C72Reader.java) |
| Read-only HTTP routes and browser records view | [DashboardServer.java](app/src/main/java/be/keypharm/rfid/DashboardServer.java), [dashboard.mjs](app/src/main/assets/dashboard.mjs) |
| Screen styling and shared color tokens | [style.css](app/src/main/assets/style.css) |

The CSV template uses `pallet_ref,pallet_epc,carton_ref,carton_epc,sku` with one row per carton. A file can contain several pallets. The Test lead can revise the manifest after a scan, until a clean match is confirmed: a revision needs a reason and a new verification and pallet identification, and every run keeps the revision it was scanned against, also in the export. Headers are case-insensitive, commas or Excel semicolons both work, SKU may be blank, and every bad row is listed at once. The template is available in the app. Simulation uses a synthetic sample. An internal build can bundle a confirmed hardware CSV as `app/src/main/assets/private-live-sample.csv`. It is ignored by Git and made available from **Use live sample** in hardware sessions. The confirmed set contains one pallet and 13 cartons. The source XLS reported 28 unique EPCs and the operator reported 27 physical test tags. Treat the still-unidentified extra EPC and the remaining physical set as unverified. Demo allocation counts cartons, one pallet tag, candidates and reserves across sessions. A pre-scan revision replaces the session's current allocation. Actual treatment of already-used tags and replacements is still open.

The app retains completed attempts and audit events locally. During a hardware run, observations are periodically checkpointed. A restarted app marks an unfinished run as Interrupted and retains the last checkpoint. Each run stores the region, power and device ID read back when that run started. A new unique EPC gives a short beep and vibration; an interrupted run gives an error tone. Export produces the section 8 evidence CSV, the full records CSV and a readable summary through Android's share sheet.

Dashboard sharing uses a private link on port 8787 on the same trusted Wi-Fi. Since 0.8.0 it shares every committed record, hardware sessions included (before, it showed only sample simulation sessions, so a C72-only device showed an empty dashboard); the Test lead can untick **Include hardware and imported records** before sharing to limit it to samples. The dashboard has no record editing or scan controls. The handheld shows the link as a QR code too. Stop sharing when finished. Both screens use the official KeyPharm logo from keypharm.com (`keypharm-logo.png`, 339 × 133 px, byte-identical to the site file; the site has no larger or vector version). The handheld header shows `keypharm-logo-hd.png`, made from it by `python tools/logo-hd.py`: white box removed, cropped to the ink, upscaled 3× (681 × 150 px), shown 44 px tall (34 px on phones). Swap in a vector logo when Keypharm supplies one. The WebView only serves files listed in `MainActivity.ASSETS`; 0.8.0 shipped the new logo without listing it, so it did not render on the C72 (fixed in 0.8.1). `tests/browser_smoke.py` now fails if a file the handheld loads is missing from that list. Splash (Android 12+, 0.8.1): `Theme.Keypharm` (`res/values-v31/themes.xml`) shows the white KeyPharm mark (`drawable/ic_splash.xml`) on KeyPharm green, then the light app ground, so there is no white flash. The launcher icon is a vector of the KeyPharm mark ([brand spec](.hallmark/brand-spec.md)).

## Build and run

To generate manifests on a PC from a Chainway UHF `.xls` export, put the workbook in the repository folder as `input.xls`. With `uv` installed, run the [converter](tools/uhf-xls-to-manifests.py) from PowerShell.

```powershell
uv run --with xlrd python tools/uhf-xls-to-manifests.py input.xls build/live-manifests
```

The converter uses workbook order, with up to 14 tags per pallet by default. It uses the first EPC in each group as the pallet tag and the rest as cartons. Check the assignments against the physical tags, then copy the generated CSV to the C72. In a hardware session as Test lead, select **Choose CSV → Save manifest**. To generate the CSV directly on the C72, select **Build from scan → Save CSV file** in the Cartons step of a hardware session.

Follow the [README](README.md) for the demo walkthrough, SDK dependency and build commands. Use JDK 17, Android SDK 34 and the Chainway `DeviceAPI_ver20251103_release.aar`. Put the AAR in `app/libs`. The repository does not carry a copy of the vendor AAR, the generated APK, or the signing key. The Windows SDK build script produces a signed debug APK at `build/keypharm-poc-<versionName>-debug.apk`. Keep the same local signing key when updating the installed package `be.keypharm.rfid.poc` so Android can preserve its data. For a build that installs next to it, pass `-Package be.keypharm.rfid.poc.dev -Label "Keypharm RFID POC Dev"` (output `build/keypharm-poc-<versionName>-dev-debug.apk`).

Build only the Dev package (`-Package be.keypharm.rfid.poc.dev`) from `Downloads/KeyPharm-repo`: its `build/debug.keystore` signed the Dev app installed on the C72, and a different key makes `adb install -r` fail. The separate Reset package (0.8.1) is retired since 0.8.2; do not rebuild it.

On the C72, open **Keypharm RFID POC → Sessions → Evidence → Share web dashboard**. Copy the link and open it in a browser on the same Wi-Fi. Keep the handheld app running. Simulation mode supplies a matching pallet and selectable missing, extra, clean and interrupted carton scenarios.
